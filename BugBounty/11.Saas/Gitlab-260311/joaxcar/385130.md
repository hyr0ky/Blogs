## Report

####  Summary

When configuring an `On demand DAST scan` (see [docs](https://docs.gitlab.com/ee/user/application_security/dast/index.html#on-demand-scans)) the user configuring the scan can enter both username and password and a list of custom request headers.

Both the password and the custom request headers are masked in the UI, and are not possible to view after being saved (not even by the user who configured the scan). Note that to even be able to view  `On demand DAST scan` configs a user needs to have at least `Developer` access to the project.

But when a scan runs it creates some log files, it seems to differ what type depending on if it is a `website scan` or an `API scan`. The `website scans` leak custom headers.

When a user configures a `Site profile` (see [docs](https://docs.gitlab.com/ee/user/application_security/dast/index.html#site-profile)) the user can add headers and password that the docs describe in this way

> When configured, request headers and password fields are encrypted using aes-256-gcm before being stored in the database. This data can only be read and decrypted with a valid secrets file.

But they headers will be present in clear text in job logs accessible by unauthenticated users (on a public project)

On a `website` target the headers are printed in clear text here https://gitlab.com/ultimatetest7/hen/dast/-/jobs/3287276071 in the job log. But the password is masked, and no artifacts are created.

####  Impact

DAST scan job logs leak headers to deploy environments 

####  Examples

####  What is the current *bug* behavior?

Headers are printed in clear text (or base64) in job log files open to all users

####  What is the expected *correct* behavior?

Headers should not end up in the logs

## How To Reproduce

Please add [reproducibility information] to this section:

1. Log in as a victim user.  
2. Create a new public project (you need Ultimate subscription)  
3. Go to https://gitlab.com/GROUP/PROJECT/-/on_demand_scans/new  
4. Configure all fields for a web scan
5. Add a custom header
6. Click `save and run scan`  

7. Go to https://gitlab.com/GROUP/PROJECT/-/pipelines  

8. Click the new pipeline and then click on the DAST job  
9. When the job finishes, search for CustomHeaders
10. Your header should now be visible in the log in the clear tesxt  
11. Visit the log as an unauthorized attacker in another browser to see that it is leaking
