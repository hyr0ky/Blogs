## Report

##### Summary

Hi team, after reviewing the latest patch against ["ATO in Web-IDE using XSS in .ipynb files"](https://hackerone.com/reports/2765778) I found another way to achieve the same impact. It utilized another path in the code that was not used or patched last time

I believe that this is the fix for the previous report

https://gitlab.com/gitlab-org/gitlab-web-ide-vscode-fork/-/merge_requests/107

This patch adds a `freeze` for the `Map` object but, more importantly, replaces the `remoteAuthority` parameter with an empty string

```
const remoteAuthority = ''; // searchParams.get('remoteAuthority');  
```

This effectively blocked the previous report. However, I found a way to use the `resourceBaseAuthority` parameter in combination with a CSP bypass to arrive at the same impact.

Note that the details section should be read in the context of previous reports. To just verify the attack skip to POC

##### Details

First of, I found that its possible to trigger the path traversal in `fetch requests`(see the previous report) using `/%2e%2e/` as a pattern without hooking into any javascript objects.

The `resourceBaseAuthority` parameter can be used to hit this part of the `service worker` code in `workbench/contrib/webview/browser/pre/service-worker.js`

```javascript
switch (event.request.method) {  
			case 'GET':  
			case 'HEAD': {  
				const firstHostSegment = requestUrl.hostname.slice(0, requestUrl.hostname.length - (resourceBaseAuthority.length + 1));  
				const scheme = firstHostSegment.split('+', 1)[0];  
				const authority = firstHostSegment.slice(scheme.length + 1); // may be empty  
				return event.respondWith(processResourceRequest(event, {  
					scheme,  
					authority,  
					path: requestUrl.pathname,  
					query: requestUrl.search.replace(/^\?/, ''),  
				}));  
			}  
			default: {  
				return event.respondWith(methodNotAllowed());  
			}  
		}  
```

where we can control the `scheme`, `authority` and `path` by making the initial XSS do a fetch request of an URL of the format `https://https+gitlab.com.com/assets/webpack/gitlab-vscode/0.0.1-dev-20250109231656/vscode/extensions/ipynb/%252e%252e/%252e%252e` given a `vscode-resource-base-authority=com`

The problem is that requests to `https://https+gitlab.com.com` will get blocked by the CSP `connect-src`. To bypass the CSP we can take advantage of other files stored on the same domain that is not subject to CSP. Such as `workbench/contrib/webview/browser/pre/fake.html`.

If we frame `workbench/contrib/webview/browser/pre/fake.html` we can then write a script tag to the body of this new frame and have it execute without CSP. We can then fetch the resource using the `https://https+gitlab.com.com` domain, hit the path traversal and retrieve a CSRF token as in the previous reports.

The full flow of the attack is this

1. XSS in `ipynb` file triggers when victim views the file in Web-IDE
2. The XSS removes the old service worker and registers a new version of the same worker but using the URL parameter `vscode-resource-base-authority=com`
3. The XSS is used to create a new `iframe` pointing to `/workbench/contrib/webview/browser/pre/fake.html`
4. The XSS is used to write a new script into the body of this new iframe. This will then execute without CSP
5. The script in the new iframe will make a fetch request like this

```javascript
fetch("https://https+gitlab.com.com/assets/webpack/gitlab-vscode/0.0.1-dev-20250109231656/vscode/extensions/ipynb/" + "%252e%252e/".repeat(20) + "-/profile/emails")  
```

the response will contain the victims `CSRF` token\
6. The script in the new iframe now navigates the `parent.parent` to an attacker-controlled page leaking the `CSRF` token.\
7. The attacker page (that is now framed on the page) directly use the`CSRF` token to register a new email to the victim account. Full ATO

The chain is a bit complicated, but it all happens automatically by just visiting the page in step 1. No further interaction is required.
