## Report

####  Summary

Its possible to configure Gitlab to use a proxy server for `image` content linked in descriptions and discussions. See [docs](https://docs.gitlab.com/ee/security/asset_proxy.html)

Given the docs this example configuration is given:  
```bash  
curl --request "PUT" "https://gitlab.example.com/api/v4/application/settings?\  
asset_proxy_enabled=true&\  
asset_proxy_url=https://proxy.gitlab.example.com&\  
asset_proxy_secret_key=<somekey>" \  
--header 'PRIVATE-TOKEN: <my_private_token>'  
```  
which would put the proxied requests under the domain `https://proxy.gitlab.example.com` given an instance on `https://gitlab.example.com`

The documentation tells users to use `go-camo`.

Any content proxied through the proxy will be served with "safe headers" and a `CSP` like this (per default):  
```  
Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline'  
```  
On gitlab.com the proxy server is on `https://user-content.gitlab-static.net/` and is served with the CSP  
```  
media-src 'self'; script-src 'none'; object-src 'none'  
```

None of these CSP's will block `form actions`. This allows a malicious user to host `forms` on these subdomains.

On gitlab.com, this does not have a great impact as the top domain is `gitlab-static.net`, but on self-hosted instances that follow the documentation, they might use `proxy.toplevel.com` instead. Using a subdomain of the main domain will allow most password managers to autofill (and potentially auto-submit) forms as they are usually `lax` in what domains they hit.

Worst case, it could lead to automatic credential theft; best case, it's a form of injection that could be used for phishing or other activities.

I believe you should make sure that any `CSP` on these domains are blocking `form-actions`

####  Steps to reproduce

To test this on gitlab.com

1. Create a new `issue` in any project  
2. In the description type this (or any link to your own hosted SVG file with HTML content)  
```html  
<img src="https://joaxcar.com/temp3.svg">  
```  
3. Click create  
4. When the page loads click on the image that look like a form  
5. You should end up on a page like `https://user-content.gitlab-static.net/2984931a8e1d4162aa4def42cd42566626b10223/68747470733a2f2f6a6f61786361722e636f6d2f74656d70332e737667` containing a form  
6. Fill the form and click `Submit` and the form will send your data to `example.com`

This just proves that you can store any form of HTML content on the proxy domain, and that forms can be submitted. If you want to test this using password managers you need to follow https://docs.gitlab.com/ee/security/asset_proxy.html to set it up on your local instance under a subdomain of your main instance domain.

####  What is the current *bug* behavior?

The proxy endpoints will per default allow HTML in SVGs and be served with a CSP that will not block `form actions`

####  What is the expected *correct* behavior?

Users should not be able to serve interactive `forms` under the proxy domain

####  Output of checks

this bug happens on GitLab.com

####  Impact

HTML injection with `form action` CSP bypass can potentially leak victims credentials under default configuration
