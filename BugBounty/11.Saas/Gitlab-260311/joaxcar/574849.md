## Report

#####  Summary

Gitlab.com usually uses the [asset proxy](https://docs.gitlab.com/security/asset_proxy/) to render user-supplied images and videos. The proxy is explained like this in the docs

> A possible security concern when managing a public-facing GitLab instance is the ability to steal a user’s IP address by referencing images in issues and comments.  
> One way to mitigate this is by proxying any external images to a server you control.

But the asset proxy also helps protect against `HTTP 401 attacks` where a subresource requests authentication through the browser auth dialog.

Any user content that is rendered as Gitlab Flavoured Markdown will be protected by this by always defaulting to the asset proxy.

The new agent session page does however, use a different markdown parser. The `NonGfmMarkdown` from `app/assets/javascripts/vue_shared/components/markdown/non_gfm_markdown.vue`. This markdown parser will not turn image tags into asset proxy tags, but instead just return the plain imgage tag like this

```  
input: <img src="https://gittlab.com/auth/duo.svg">

output: <img src="https://gittlab.com/auth/duo.svg">  
```

So by triggering an `agent session` with this input `<img src="https://gittlab.com/auth/duo.svg">` we get this when visiting the session page

![Screenshot_2025-10-07_at_12.19.11.png](https://h1.sec.gitlab.net/a/0aedb4d2-c4dc-43b5-be4c-6b49df6ef5e8/Screenshot_2025-10-07_at_12.19.11.png)

(Note that the auth popup will show the attacker's domain. But the URL bar still shows gitlab.com. It is not hard to confuse a victim, as seen in the image. I have registered the URL `gittlab.com` that is hard to distinguish from `gitlab.com` in the auth popup.)

The auth popup is possible by having the image on my server respond with a `Link` header like  
```  
Link: <https://gittlab.com/auth/test>; rel=preload; as=track; fetchpriority="high"  
```  
Chrome will not trigger the auth popup if you return 401 on the actual image request. Instead, we request a subresource as a `preload`, in this case, a `track`. This is allowed as gitlab.com CSP allows any URLs as `media-src`

```  
media-src: 'self', data:, blob:, http:, https:  
```

![Screenshot_2025-10-07_at_12.21.15.png](https://h1.sec.gitlab.net/a/a4a1e1b6-4076-4e58-b903-d376e16a62be/Screenshot_2025-10-07_at_12.21.15.png)

To fix this, you could either block `media-src` and restrict it similarly to `style-src` or make sure that the `NonGfmMarkdown` obeys the asset proxy

If a user follows the instructions and fills out the auth form, their username and password will be sent to the attacker's server.

#####  Steps to reproduce

(Use Chrome)

1. Create a new Ultimate trial group on gitlab.com  
2. Create a new project in the group  
3. Go to https://gitlab.com/explore/ai-catalog/agents/ and click `New Agent`  
4. Select the project in the Ultimate trial group you just created, name it test agent and fill out the form with anything. Keep the agent `private` to not pollute the public list. Give it a name you recognize like `POC image injection`  
5. When you have created the  agent search for it in the list  
6. Click the three dots in the list and pick `test run`

![Screenshot_2025-10-07_at_13.15.06.png](https://h1.sec.gitlab.net/a/99cf4855-6959-46d3-bfbb-6a1b45f78f6a/Screenshot_2025-10-07_at_13.15.06.png)

7. In the input box just put `<img src="https://gittlab.com/auth/duo.svg">` and submit it  
8. Go to your project from step 2 and click on `Automate -> Agent Sessions`

![Screenshot_2025-10-07_at_13.16.36.png](https://h1.sec.gitlab.net/a/967d41aa-51d8-4ecb-afed-54bd29513d17/Screenshot_2025-10-07_at_13.16.36.png)

9. Wait for the session to complete its pipeline  
10. When the session is finnished click it  
11. You should see an auth popup and an image asking you to authenticate

![Screenshot_2025-10-07_at_12.23.23.png](https://h1.sec.gitlab.net/a/4a168572-5104-49c1-8d16-0242e9f14f17/Screenshot_2025-10-07_at_12.23.23.png)

#####  Impact

Rendering external images, leaking user IP,s and triggering an authentication pop-up that can leak user credentials

#####  What is the current *bug* behavior?

`NonGfmMarkdown` will render non-proxied images that allow attackers to control subresources and conduct `401 attacks`

#####  What is the expected *correct* behavior?

`NonGfmMarkdown` should obey the asset proxy rules or not allow images at all


#####  Output of checks

This bug happens on GitLab.com

#####  CVSS discussion  
I think this is a `high` impact vulnerability because of how it can be abused on gitlab.com. I put `AC` to `Low` and `Scope` to `Unchanged`. The `Scope` is, in a way, changed just as with XSS vulnerabilities, as the image injection triggers a browser's behaviour that is the auth pop-up, but then in the end, the leaked credentials are for gitlab.com again. I will leave that to you to decide.
