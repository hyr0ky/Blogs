## Report

####  Summary

I am just starting to look at the Duo AI capabilities, so bear with me if I have not fully understood the threat model yet.

On a Premium or Ultimate license group there is the option to restrict access to the Group and the groups projects using a IP restriction list. See [documentation](https://docs.gitlab.com/ee/user/group/access_and_permissions.html#restrict-group-access-by-ip-address). Enabling this on a group will prevent all access to issues and epics in the group when not requesting it from inside that IP range.

Issues in the project are not accessible through either the UI or any API.

What I noticed is that the Duo chat is not restricted by IP block lists. Thus, these two scenarios will allow for a bypass:

1.  A member of a `private` IP-restricted group can access all issues and epics from outside the IP range using `Duo Chat`  
2. Any member on the GitLab instance can access issues and epics from `public` projects even if they are behind an IP restriction

Number 2 here is worse than number 1, but the documentation for IP restrictions does state that  
> While IP restrictions apply to public projects, they aren’t a complete firewall and cached files for a project may still be accessible to users not in the IP block

Still, there might exist groups that rely on IP blocklists to work as a sort of  `internal` accessibility, even on GitLab SAAS.


#####  Steps to reproduce

0. To access `duo chat` a user needs to be member of a group with at least Premium subscription and where `Experimental features` are turned on. See [link](https://docs.gitlab.com/ee/user/ai_features.html#enable-aiml-features)

1. Create two accounts on https://gitlab.com, and make sure that both have an Ultimate trial (this is to get access to Duo chat)  
2. Log in as the victim and create a group with an `Ultimate` license (make it `public`)  
3. Create a project in the group (make it `public`)  
4. Create an issue in the project  
5. Go to https://gitlab.com/groups/GROUPNAME/-/edit and expand "Permissions and group features"  
6. Enter `1.1.1.1` in the `Restrict access by IP address` field. Scroll down a bit and click `Save`  
7. Now try to access https://gitlab.com/GROUPNAME/PROJECTNAME/-/issues/1  
The user will be blocked

8. Now log in as the `attacker` user. This user is not a member of the restricted but public group  
9. Try to access https://gitlab.com/GROUPNAME/PROJECTNAME/-/issues/1 the user will get a 404  
10. Open Duo Chat (either in top right or under "help")  
11. Type this in chat  
```  
Summarize: https://gitlab.com/GROUPNAME/PROJECTNAME/-/issues/1  
```  
12. Duo chat will think for a bit and then give you a summary of the issue

#####  Impact

Users can bypass IP blocklist using Duo Chat, leaking issues and epics to users outside the IP range

#####  What is the current *bug* behavior?

Duo chat does not seem to care about IP blocklists

#####  What is the expected *correct* behavior?

Duo Chat should check where the user is located when making requests for issues and epics

## Implementation Proposal

Create a Sidekiq middleware, which would assign the IP address to `Gitlab::IpAddressState.current`. The IP address is available from `meta.remote_ip` which is part of the job. This will be done in the public repository because we want to guard this logic by a feature flag (default enabled).
