Hi GitLab Security Team,

### Summary

This time, I found an interesting DOS vulnerability. Any user of the GitLab instance can craft a malicious audit event, such that the audit event page for admins is not available anymore and will return a `500` error for any subsequent requests.

### Steps to reproduce

1. As an ordinary user, create a new project, create a milestone, push some code  
2. Create a release on that project with an attached milestone. 

```bash  
curl -X POST -H "Private-Token: <Private-Token>" https://example.gitlab.com/api/v4/projects/<project-id>/releases?tag_name=<v1.0>\&description=Public-release\&milestones[]=My-Milestone  
```

3. As an admin user, visit `https://example.gitlab.com/admin/audit_log`

This now returns a `500` error, this the audit event log page is not available anymore. Creating a release with an attached milestone crafts a malicious audit event log entry, which is preventing the audit page to load.

### Impact

**Any** user of the instance can DOS the audit event log page of the admin by creating a malicious event log entry.

### What is the current *bug* behavior?

A malicious audit event entry can DOS the audit event log page.

### What is the expected *correct* behavior?

It should not be possible to craft a malicious event log entry.
