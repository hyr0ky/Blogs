Hi GitLab Security Team,

### Summary

I found a way to bypass the Todo redaction within GitLab. Normally, GitLab removes Todo  after a one hour grace period when a user for example leaves a project or does not have access to the feature anymore. However, this is not applied in the case of sharing a group with a group. If a group is shared within a group, the group members receive Todos, e.g., when they are mentioned on issues.

However, when the shared group is removed from the group, Todos for all group members persist. By using the REST API of GitLab, a user can get much more associated information of the Todo. He now can receives for example the full issue, including the title, and description. Note, this is always the fresh and most recent version, which might have changed after the group was removed from the group. 

### Steps to reproduce

1. Create a private group named `group_a`  
2. Add a user `foo` with `Developer` rights to to the private group `group_a`  
3. Create a private group `group_b` and inside a private project `project_b` with some issues  
4. Go to the member page of `group_b` and invite the group `group_a` with `Developer` rights  
5. As user `foo` go to `group_b/project_b`'s issue page and add a personal Todo via the `Add a To Do` button in the sidebar of the issue  
6. As the group owner, remove the group `group_a` as a member from `group_b`  
7. Wait for one hour grace period  
8. As the user `foo`, perform the following API call: `curl --header "PRIVATE-TOKEN: <TOKEN>" https://example.gitlab.com/api/v4/todos`

This now returns the old Todo from the previously shared group, which you don't have access to anymore.

* Merge requests

### Impact

The impact of this vulnerability is actually quite high. A malicious user of the group, can simply add a personal todo on all issues and merge requests of the project. This can easily be one `Add a To Do` in the sidebar of an issue or merge request. After the group is removed from the project, the malicious user has access to all issues and merge requests. Note, this always returns the most recent version of the issue or merge request! The impact of this is higher to the one in #722001, as a malicious can add Todos on not just a single project but instead of all projects of the shared group. By using the REST Todo API (https://docs.gitlab.com/ee/api/issues.html#create-a-todo) an attacker can simply create a daily job to automatically mark todos on all resources he as access to. As the information disclosure is much larger (access to all projects of a group), I am rating this one as a `High` compared to  #722001 where the access only affects one project.

    /cc to [@]jmatos who dealt with #722001

### What is the current *bug* behavior?

Todos are not redacted when the shared group is removed as a group member.

### What is the expected *correct* behavior?

When the group is removed from the other group, wait for the 1h grace period, and then GitLab should remove all todos on the group for the group members.

### Output of checks

This bug happens on GitLab.com running on GitLab Enterprise Edition 12.7.0-pre 8f00d67c760.
